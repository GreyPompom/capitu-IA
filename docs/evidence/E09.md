**Responsável técnico:** Emely  
**Data:** 05/11/2026  
**Status:** concluída tecnicamente; robustez de retentativas, rate limit e cache pertence à E10.

## Alinhamento ao escopo

A E09 conecta o fluxo aprovado: mensagem → interpretação híbrida → extração → diálogo → Open Library → normalização → resposta HTTP. O sistema mantém as quatro intenções do MVP e não cria busca por ISBN, recomendação personalizada, acervo institucional, empréstimo, reserva ou resposta generativa.

A Open Library continua sendo somente a fonte de metadados. A decisão local da CAPITU combina TF-IDF/cosseno, política de fora de escopo/ambiguidade e regras explícitas de alta precisão para comandos inequívocos. Uma regra pode aceitar uma intenção mesmo quando o score lexical é baixo; nesse caso o score continua sendo similaridade diagnóstica e a margem fica nula — ele não é apresentado como probabilidade.

## Composição implementada

| Camada | Papel na E09 |
| --- | --- |
| `nlp.interpretation` | Aplica política E05 primeiro; depois aplica regras estritas para título, autor, assunto e detalhe; chama a E06 para extrair parâmetros. |
| `app.chat_service.CapituChatService` | Orquestra as camadas sem colocar regra de negócio na rota FastAPI. Aceita catálogo injetado em testes. |
| `dialogue.manager` | Pergunta parâmetro ausente, registra resultados, resolve seleção e mantém sessão. |
| `services.open_library` | Realiza consulta real em produção ou controlada por `MockTransport`/fake nos testes. |
| `responses.templates` | Gera texto determinístico, cita a Open Library e informa campos ausentes sem inventá-los. |
| `app.main` | Delega `POST /api/chat` ao serviço, preservando o contrato E01: `session_id`, `text`, `state`, `intent` e `results`. |

## Comportamentos integrados

- título, autor e assunto consultam a rota correspondente da Open Library;
- detalhes por título fazem busca; se há um resultado, consultam o detalhe por ID; se há vários, pedem seleção em vez de escolher o primeiro;
- detalhes após “o segundo” usam somente a obra selecionada na mesma sessão;
- parâmetro ausente produz `awaiting_clarification`, com `results=[]`, sem chamada externa;
- fora de escopo não chama fonte; falha da fonte retorna `source_unavailable`;
- campos como descrição, editora ou ISBN ausentes são comunicados como não fornecidos pela fonte.

## Validação ponta a ponta controlada

`tests/test_chat_integration.py` injeta `FakeCatalog` e verifica, sem rede:

1. `Procure Dom Casmurro` → título extraído → busca por título → resposta com origem;
2. `Quais livros Machado de Assis escreveu?` → busca de obras, não biografia;
3. `Mostre livros sobre ficção científica` → busca por assunto;
4. `Quem escreveu Dom Casmurro?` → busca de título → detalhe por ID → autoria/fonte;
5. `Busque um livro` → pedido de título → resposta curta conclui a busca, sem chamada prematura;
6. busca múltipla → `o segundo` → `Quem escreveu?` usa o ID da sessão correta.

Os testes HTTP de contrato foram atualizados para usar serviço controlado, para não chamar a fonte externa. A execução do `TestClient` neste computador continua limitada pelo ambiente Python 3.14 já registrado nas evidências anteriores; o fluxo completo é testado diretamente no serviço e deve ser repetido no ambiente virtual padrão antes da entrega.

## Limites deixados para E10 e posteriores

Não há retentativa, `Retry-After`, rate limiter compartilhado ou cache nesta task. Esses controles, além de maior tratamento de timeout/429/5xx, serão implementados na E10. A UI já mantém o mesmo contrato, mas a validação visual integrada continua responsabilidade das tasks de Millena.
